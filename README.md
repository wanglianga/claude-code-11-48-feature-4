# 罕见病多中心登记数据受控分析与结果审查平台

六家医院协作的罕见病登记数据分析平台。各中心数据**不出院**：统计请求被编排到
中心本地代理执行，只有聚合统计量进入受控工作区；输出表经小样本抑制与结果审查
后才可发布，发布报告引用完整运行版本（规则版本、批次快照、审查决定、内容哈希）。

## 架构

```
┌────────────┐   ┌─────────────────────────────────────────────┐
│ React 前端  │──▶│ FastAPI 后端（编排运行 / 审查 / 发布）        │
└────────────┘   │  PostgreSQL：元数据、运行快照、审查记录        │
                 └───────┬─────────────────────────────────────┘
                         │ HTTP（仅下发规则+统计请求，仅回传聚合量）
        ┌────────┬───────┼────────┬────────┬────────┐
        ▼        ▼       ▼        ▼        ▼        ▼
     agent-C1 agent-C2 agent-C3 agent-C4 agent-C5 agent-C6   ← 中心本地执行模拟器
     （每个 agent 只读本中心 registry.csv；C2 结局用本地编码、
       C5 缺实验室指标字段、C6 为小样本中心）
```

- **数据管理员**：登记中心批次、变量字典与可用范围，锁定批次（锁定后不可变）。
- **研究者**：编辑队列规则（并发编辑走条件级三方合并）、提交统计请求、创建输出表。
- **结果审查员**：审批规则版本；对小样本/可差分推回的输出做合并、抑制或拒绝；
  批准后输出即发布，报告含完整溯源与哈希。

关键语义：

- 运行启动时**快照各中心已锁定批次**；运行中替换批次只影响新运行。
- 中心执行失败或缺变量映射 → 标记为**覆盖缺口**（`missing_mapping`/`failed`），
  不计为零例，总计只汇总成功中心并在结果中显式列出未纳入范围。
- 输出表任一单元格 `0 < n < k`（默认 k=5）或**唯一隐藏格可由合计差分推回**时，
  审查队列阻止放行，须合并分组、抑制单元格（必要时连合计一起抑制）或拒绝。
- 两名研究者并发改同一规则：后到保存收到 **409 + 条件级差异 + 自动合并建议**，
  确认合并后才能落库；已进入审核的排除条件不能被后一次保存静默抹掉。

## 严重不良事件（SAE）裁定工作流与竞争风险数据服务（Feature 4）

临床专家比较治疗后一年内的严重不良事件时，同一患者可能先有轻微症状、后被外院诊断为
严重事件，也可能在确认前死亡或失访；各中心对首发日期、严重程度、死因的上报时点不一。
本特性在**冻结的随访记录与受控分析运行之上**新增一条独立、可追溯的事件处理链，分五层
各自持有状态：

| 状态层 | 落地对象 | 职责 |
| --- | --- | --- |
| ① 候选接入 | `EventIntakeBatch` / `EventCandidate` | 中心本地 `events.csv` 保存原始候选（发生/知晓时间、严重程度证据、死亡记录、外院回执）；受控区只保存带行哈希与整批快照哈希的审计副本 |
| ② 实体去重 | `EventCluster` / `EventClusterMember` | 并查集按显式 `linked_candidate_id` 与共用外院/转院回执融合；**同一临床事件跨院只计一次** |
| ③ 裁定队列 | `AdjudicationTask` / `AdjudicationVote` | 共同规则 **AR-v1** 自动按最早满足阈值的记录定事件日；冲突候选进**盲法专家**队列，两人一致结案，分歧由首席专家终裁 |
| ④ 不可变清单 | `AdjudicationSnapshot` / `…Item` | 冻结为带内容哈希的裁定清单；运行只引用清单，**运行中途完成的裁定只能进入下一次运行** |
| ⑤ 统计风险集 | `RunRiskResult` → 输出审查 | 各中心在本地用本中心裁定记录算竞争风险集，只回传统计量 |

AR-v1 把每个去重簇分为五类：**已裁定事件 / 待裁定 / 非事件 / 竞争终止（死亡）/ 信息不足**；
随访类记录另归**删失（失访、分析截点）**与**无法判定（转院）**。死亡、失访、转院**绝不并入
“未发生事件”**。事件日取**最早满足严重程度阈值记录的发生日**，而非外院回执的获知日；
运行可选择**事件发生时间（occurrence）**或**获知时间（awareness）**作为时间基准，并在
审查输出中显式声明，同时报告待裁定候选数与各中心事件确认覆盖率。

自动模式（规则）速度快且一致，但在外院晚回执、重复住院、严重程度升级中易误判——因此凡
重度记录与轻度随访备注相互矛盾者一律转人工盲法，语义更准确但会延迟可分析样本。

内置验收样例（`center_agent/center_agent/eventgen.py`）：

- **S1 外院晚回执**（C1、C5）：事件日=最早重度发生日，不等于回执获知日；
- **S2 同一事件双中心上报**（C2↔C4，共用回执 `XFER-2210`）：融合为单簇只计一次；
- **S3 死亡先于确认**（C3）：竞争终止；
- **S4 严重程度升级 + 重复住院**（C1）：在重度升级日自动确认；
- **S5 裁定意见分歧**（C2）：盲法投票分歧 → 首席终裁；
- 另有失访（删失）、转院（无法判定）、信息不足样例覆盖全部类别。

## 一键启动（Docker Compose）

```bash
docker compose up --build
```

- 前端：http://localhost:8080 （后端 API：http://localhost:8000）
- 首次启动自动：建库建表 → 生成六中心虚构数据 → 注册并锁定首批次 → 写入演示账号与一条已批准规则。

C2 批次更新演示（替换数据 → 登记新批次 → 新运行自动引用）：

```bash
docker compose run --rm datagen python -m center_agent.datagen --root /data --center C2 --seed 43
# 然后用 admin 登录 → 数据与批次 → C2「从中心同步」→「锁定」
```

## 本地开发启动

预装运行时：Python 3.12（`/opt/python-3.12`）、Node 22（`/opt/node-22`）、
PostgreSQL 18（`127.0.0.1:5432`，库/用户/密码均为 `ccdev`）。

```bash
# 1) 依赖（首次）
/opt/python-3.12/bin/python3 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt -r center_agent/requirements.txt
cd frontend && npm install && cd ..

# 2) 生成虚构中心数据（首次）
PYTHONPATH=center_agent .venv/bin/python -m center_agent.datagen --root data/centers

# 3) 一键启动 6 个中心代理 + 后端（:8000）
bash scripts/dev.sh            # 追加 --frontend 可同时起 vite 开发服务器(:5173)

# 4) 停止
bash scripts/stop.sh
```

后端启动时自动建表并种子（用户/中心/字典/映射/锁定批次/一条已批准规则）。
前端开发模式 `npm run dev`（代理 /api 到 8000）；或 `npm run build` 后由后端直接托管。

## 验证方式（本题验收场景）

### 自动化验证（已实际执行）

```bash
.venv/bin/python -m pytest backend/tests -q     # 26 项单元/接口测试（17 基线 + 9 事件裁定）
.venv/bin/python scripts/smoke.py               # 33 项端到端冒烟（需平台已启动）
```

基线冒烟覆盖：四角色登录、六中心锁定批次、全量运行、C5 缺字段→覆盖缺口而非零例、
批次替换后旧运行快照不变/新运行用新批次、运行对比、并发保存 409+条件级差异+
确认合并、在审排除条件删除需确认、小样本输出被拦截、合并+抑制后放行、
发布报告溯源完整且哈希校验一致。

Feature 4 冒烟额外覆盖（`backend/tests/test_adjudication.py` 与 `scripts/smoke.py`）：
六中心事件候选审计接入与快照哈希、S1 外院晚回执事件日、S2 双中心去重计数一次、
S3 死亡先于确认→竞争终止、S4 升级自动确认、失访/转院/信息不足分类、S5 盲法投票分歧与
首席终裁、首份清单保留待裁定、竞争风险五类互斥且穷尽、运行冻结边界（中途裁定只进下一次
运行）、发生/获知时间基准切换、各中心确认覆盖、裁定清单与发布报告哈希均可复现校验。

### 事件裁定手工核对路径

1. **候选接入与去重**：`admin` 登录 → 事件裁定 → 逐中心「从中心接入/刷新」；
   在去重簇表展开 `CL-C2-EVT-S2-01`，可见 C2/C4 三条候选因共用回执 `XFER-2210`
   融合为一个跨院簇；`CL-C1-EVT-S1-01` 的事件日为最早重度发生日（非外院获知日）。
2. **盲法裁定分歧**：用 `adjudicator1`、`adjudicator2` 登录 → 盲法裁定 →
   对 `CL-C2-EVT-S5-01` 分别投「已裁定事件」「非事件」→ 状态变 `in_review（分歧）`，
   非首席账号终裁被拒；换 `chief` 终裁后结案，投票在结案后才互相可见。
3. **冻结与运行**：`researcher1` 登录 → 事件裁定「冻结当前裁定为新清单」→
   运行页选「严重不良事件·竞争风险运行」，选清单与时间基准（发生/获知）启动；
   运行详情显示时间基准、待裁定数、各中心确认覆盖与五类互斥计数。
4. **运行冻结边界**：先启动一次运行（含 1 待裁定），再到盲法页完成该候选终裁，
   回看重运行的清单与计数不变；冻结新清单并发起下一次运行，事件数 +1、待裁定清零。
5. **审查与溯源**：对竞争风险运行提交输出表 → `reviewer` 抑制小格后批准 →
   已发布报告的 provenance 内含 `adjudication`（清单版本/哈希、时间基准、待裁定数、
   六中心确认覆盖），报告哈希校验一致。

### 手工核对路径

1. **中心批次更新**：`admin` 登录 → 数据与批次 → C2「从中心同步」→「锁定」；
   旧运行详情批次快照不变，新运行 C2 引用新批次；运行对比页可见差异。
2. **并发改规则**：两个浏览器分别用 `researcher1`/`researcher2` 打开同一规则，
   先后保存 → 后者看到条件级差异弹窗 →「采用自动合并结果」→ 再保存；
   若合并结果删掉了在审排除条件，会再要求显式确认，且原在审版本保留。
3. **单中心缺字段**：新建运行勾选「实验室指标均值」→ 运行状态为
   「完成（有覆盖缺口）」，C5 标记 `missing_mapping`，总计 = 5 家中心之和。
4. **小样本输出**：用规则「RD03 且出生年 ≥ 2005」按 路径+性别 分组运行
   （C/F=4、C/M=2 小于 k=5）→ 提交输出表 → `reviewer` 审查：直接批准被拒 →
   合并 C 两组 → 抑制剩余小格 → 批准 → 已发布报告中可见完整溯源与哈希。

## 目录结构

```
backend/          FastAPI 后端
  app/dedup.py          实体去重（并查集，跨院同事件只计一次）
  app/adjudication.py   AR-v1 规则裁定、盲法投票/终裁、不可变清单冻结
  app/competing.py      候选接入编排、风险集分发与跨中心竞争风险聚合
  app/routers/events.py 事件接入/去重簇/盲法队列/清单 API
  tests/test_adjudication.py  事件裁定与竞争风险端到端测试
center_agent/     中心本地执行模拟器
  center_agent/eventgen.py   生成六中心 events.csv（含 S1–S5 验收样例）
  center_agent/eventexec.py 本地竞争风险集计算（只回传统计量）
  center_agent/datagen.py    生成 registry.csv 并联动生成事件数据
frontend/         React + Vite（新增 Events 事件裁定页、Adjudication 盲法队列页）
scripts/          dev.sh / stop.sh 本地启停、smoke.py 端到端验证
docker-compose.yml 一键部署（db + 6×agent + backend + frontend）
```
